# Wingray 4.4.147 early-boot review

Review of the existing port, 18 October 2026. This continues source commit
`8b8f60ea`; it does not replace the donor or restart the port. No device commands,
flashing or repartitioning were performed for this review. Original boot,
recovery and the failed diagnostic image are preserved.

## Conclusion and limits

No root cause is established. The retained Motorola logo and absent USB ACM
device do **not** prove that execution stopped before the console. The existing
serial capture requires the USB PHY, controller, gadget, kernel initialization,
initramfs, Android dynamic loader and BusyBox shell to work. A failure anywhere
along that chain looks the same from the host. Ramoops is also initialized after
the earliest assembly/decompression stages. The old Android `last_kmsg` format
is not the new ramoops format; the retained old log is not a negative test for
new-kernel execution.

The highest-priority isolation is to remove unverified polling UART output,
then establish an observation point before ATAG conversion/decompression. Do not
change display, touch, Wi-Fi or regulator drivers to guess at this failure.

`scripts/audit-boot-image.py`. It checks the actual saved images and embedded
IKCONFIG, not merely the current defconfig. Hashes identify the tested candidate;
new builds must not overwrite it.

Header addresses are declarations. No trace of the bootloader's actual stores,
entry registers, CPU mode or MMU/cache state was captured. Their agreement and
successful restoration are evidence of packaging consistency, not proof of a
successful handoff.

The working image's historical SHA1 ID does not match a freshly calculated v0
ID; the diagnostic ID does. Since the working image boots, its stale ID alone
is not a reason to alter the image or blame the new kernel's failure.

### Decompression and memory

The Xoom's declared load address is outside AUTO_ZRELADDR's first-128MiB
assumption. Without a fixed destination, masking `0x10008000` with `0xf8000000`
would produce base `0x10000000` and destination `0x10008000`, inconsistent with
the original zero-based RAM layout. **The existing port already corrects this.**
The correction is present in the failed binary despite CONFIG_AUTO_ZRELADDR=y;
there is no reason to apply it a second time or change the boot header to
`0x8000` on that basis.

The diagnostic zImage ends at component offset `0x2daa40`. The appended DTB is
29,444 bytes, is eight-byte aligned at declared physical `0x102e2a40`, has valid
magic/length and is included in the Android header's kernel size. The entire
compressed component ends below the ramdisk address. The kernel Image spans
`0x8000..0x5b4fe0`; System.map places its BSS end at physical `0x5f2678` for
PHYS_OFFSET=0. Neither overlaps the incoming compressed image, tags or ramdisk.
These checks do not validate the entry cache state or arbitrary DMA activity.

The working command line supplies 1GiB at zero, bootloader framebuffer
`0x1e018000..0x1e7e7fff`, and LP0 vector `0x1e7f1020..0x1e7f301f`.
The old board reserves/removes `0x1fe00000..0x1fffffff`, uses ram_console in
its upper 1MiB, and reserves video buffers/carveout through `0x3fffffff`.
The new tree preserves these areas and parses framebuffer/LP0 boot arguments.
The new single `/memory` node avoids a duplicate `/memory@0` surviving ATAG
translation. None of these reservations collides with the verified low kernel
output range. They remain contingent on the actual command line reaching C.

### ARM handoff and machine identity

The baseline board is `MACHINE_START(STINGRAY)` with expected legacy number
2633, not a separate numeric WINGRAY board. That expected number is established
from source; r1 was not captured live. The new kernel should select the Tegra
DT machine using `motorola,wingray`, `nvidia,tegra20`. It does not need a new
numeric Wingray ID when the appended DTB reaches `setup_machine_fdt()`.
Changing r1/mach-types without first proving a missing DTB is unjustified.

The ARM protocol requires ARM instruction state, SVC mode on Cortex-A9, IRQ/FIQ
masked, MMU off, D-cache off, r0=0, r1=machine ID and r2=ATAG/DTB address.
The 4.4 hyp stub checks virtualization capabilities; CONFIG_ARM_VIRT_EXT=y is
not proof it executes HYP-only instructions on Cortex-A9. A bootloader-state,
processor-lookup, cache-maintenance or MMU-page-table failure remains possible
before C/console. Register/state breadcrumbs are needed to distinguish them.
The zero padding between sections in the zImage is not a missing decompressor:
disassembly confirms executable fixed-address instructions after it.

The decompressor recognizes the appended FDT at `_edata`, expands it for ATAG
conversion, replaces r2 with its address, and later jumps to the uncompressed
kernel. Its converter accepts ATAG_CORE (size 2 or full core), translates
ATAG_MEM, ATAG_CMDLINE and ATAG_INITRD2, and ignores unrelated vendor tags.
The original header's high tags address need not equal the old board's
`params_phys=0x100`; that is not a demonstrated incompatibility.

`scripts/test-atag-dtb.sh` executes this donor's actual converter and libfdt
against the saved DTB with synthetic public Xoom memory, command-line and initrd
tags. It passes under ASan/UBSan. **It does not verify the tablet's live r2/list.**
If translation failed, the static DT might still permit kernel boot while the
external initrd information is lost, giving a later userland failure.

## Prioritized hypotheses, not diagnoses

1. **UART polling can stall before useful output.** DEBUG_LL implicitly enables
   DEBUG_UNCOMPRESS in this tree. Decompressor `putstr()` uses Tegra UARTB and its
   busy loop has no timeout. Its clock/reset gate avoids an obviously disabled
   port, but does not bound a stuck LSR. Separately, the forced
   `earlycon=uart8250,mmio32,0x70006040` assumes initialized hardware and the
   generic transmit loop waits forever for TEMT/THRE. The working board explicitly
   configures clocks before initializing UARTB. No live entry clock/LSR evidence
   exists. UARTB address is correct; mmio32 **does** imply four-byte register
   spacing here, so a missing regshift is not the defect.
2. **Entry/ATAG/decompression/MMU failure.** Invalid r2, unexpected tag format,
   CPU/cache state or a failure before `start_kernel()` could explain the same
   symptom. Static image/ATAG tests reduce some risks but do not exclude them.
3. **SMP/L2/platform initialization.** Secondary-CPU startup, PL310 and timer/IRQ
   setup occur before the full peripheral/USB path. The old config enables
   Cortex-A9 workaround 742230 while the new SMP config does not; that difference
   merits a controlled check against actual CPU revision, not a claim that it
   caused this boot. Do not blindly copy old vendor errata options into 4.4.
4. **Later probe or userspace failure.** CPCAP, pinmux, DRM and other new probes
   are numerous independent variables. Missing USB enumeration could also mean
   a USB PHY/gadget issue or failure to execute dynamic `/init`. Neither the new
   ramdisk nor this particular USB path has an independent positive control.

## Minimal configuration and observations

The separate, successfully cross-compiled `wingray_early_defconfig` / `tegra20-motorola-wingray-early.dts`
profile retains the existing RAM/ATAG/decompression path and UARTB device, but
uses UP, disables the L2 driver, block/storage, networking, USB, input and all
new board peripheral includes. It leaves firmware power/pinmux state alone.
It enables IKCONFIG, a larger printk buffer, timestamps, `initcall_debug`,
DEBUG_FS and ramoops. It avoids pre-console UART polling by disabling DEBUG_LL
and omitting earlycon/earlyprintk. It is an isolation baseline, **not by itself
an observation channel for the first instructions**. USB enumeration is not
expected in this profile.

`wingray_early_uart.fragment` proposes DEBUG_LL, Tegra UARTB, EARLY_PRINTK and
`earlyprintk` for a second build, only after UART clock/reset/physical access and
capture are verified. It intentionally exposes the otherwise implicit
DEBUG_UNCOMPRESS change. Validate the resolved config; hidden Kconfig options
such as ARM_VIRT_EXT cannot simply be disabled by writing a defconfig line.
A UART output timeout or independent RAM markers are required before treating
absence of UART text as evidence of a CPU hang.

If UART access is unavailable, add optional, reviewed assembly RAM breadcrumbs
before another device test. A candidate is the lower part of the already
reserved legacy 2MiB console area, **after confirming bootloader ownership and
safe recovery access**. Record fresh attempt ID plus stages: zImage entry,
after CPU-mode setup, before/after ATAG translation, before/after decompression,
`sText` entry, before MMU enable and first C entry. Preserve argument registers,
do not depend on an uninitialized stack, handle cache visibility explicitly,
and plan post-MMU mappings. Implement/test these markers separately; the current
profile does not claim to include them. Do not place markers in boot/recovery,
at address zero, in the framebuffer or LP0 vector.

## Staged validation; every device write requires fresh explicit approval

1. **Offline baseline (this review):** preserve hashes, audit headers/ranges,
   disassemble both entry paths, exercise ATAG conversion and compile the isolated
   profile. No boot/recovery/partition writes.
2. **Observation first:** validate a UART capture path using the working kernel,
   or prove reserved-RAM marker recovery. Capture r0/r1/r2/CPSR and CPU ID without
   changing the bootloader or its persistent settings. A read-only working-ROM
   capture needs permission if a new device operation is proposed.
3. **Positive controls:** separately approve any test that writes boot. A
   repackaged working kernel/ramdisk can test the packer; a tested static or
   embedded initramfs can isolate external ATAG_INITRD2 and dynamic-loader issues.
   Embedded initramfs alone does not eliminate the need for valid DT boot data.
   Change one variable per image and keep each hash/artifact.
4. **Isolated 4.4:** separately approve a boot-slot test/restore procedure. Use
   the minimal profile and established observation channel, initially no USB,
   storage or new regulator/display drivers. Stop at the first missing marker;
   distinguish decompressor, head/MMU, C, IRQ/timer and initcall failures.
5. **Incremental return:** restore L2, then SMP individually. Add USB controller/
   PHY/gadget and RAM-only initramfs shell next, then read-only eMMC geometry and
   BigPart. Add pinmux, power rails, display, touch and SDIO one group at a time.
   Suspend, DVFS and charging come after stable repeated boots. BigPart never
   needs repartitioning for these tests.
6. **Rollback for every approved flash test:** verify original backup hashes and
   fastboot connectivity first; leave recovery and layout untouched; restore the
   original boot image and compare a full readback, then confirm original kernel
   and Android boot completion. Bootloader 1050 rejects `fastboot boot` on this
   device even when unlocked, so RAM boot must not be promised again. No further
   flash test is authorized by this review request.

## Reproduce review checks

```
python3 scripts/audit-boot-image.py
bash scripts/test-atag-dtb.sh
XOOM_PROFILE=early XOOM_ARTIFACT_DIR="$PWD/artifacts/boot-review-early" bash scripts/build-wingray.sh
```

The builder's early profile uses a separate destination. The diagnostic Android
image builder now requires a new `--output-dir` under ignored `artifacts/`, refuses
existing directories, and defaults to `panic=0` so a new candidate cannot silently
replace failed evidence or automatically reboot away from a panic. It performs
no device operations. These are tooling corrections, not a confirmed boot fix.

Relevant primary sources are the checked-in donor's `Documentation/arm/Booting`,
`arch/arm/boot/compressed/{head.S,atags_to_fdt.c,debug.S}`,
`arch/arm/kernel/{head.S,devtree.c}`, `arch/arm/include/debug/tegra.S`,
`drivers/tty/serial/8250/8250_early.c`, and the baseline's
`arch/arm/mach-tegra/{Makefile.boot,board-stingray.c}`. The ElementalX binary
is not claimed to be an exact build of the separately pinned Schischu baseline;
its embedded config and entry instructions were checked independently.

Build evidence: `evidence/early-profile-build-report.json` and
`evidence/early-profile-build.txt`. Source proposal is separate commit
`881f6d98` / patch `0004`; the tested hardware candidate remains unchanged.
